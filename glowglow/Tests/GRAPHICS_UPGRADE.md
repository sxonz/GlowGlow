# 그래픽 강화 검증

## 구현 범위

- 경기장: 격자와 테두리 발광을 단일 바닥 렌더러로 통합, 마젠타/청록 가장자리 흐름.
- 플레이어: 유리 같은 어두운 본체, 발광 테두리와 중심 에너지.
- 탄환: 선명한 중심광. 프리즘에는 분광 재질과 부드러운 잔상.
- 폭발/피격: 섬광, 확장 링, 바닥 잔광, 방향성 파편. 판정과 분리한 로컬 장식.
- 레이저: 얇은 전기 아크. 태양: 표면 흐름과 코로나. 참가자도 전용 재질 재현.
- 무기 바: 재사용 준비 시 짧은 청록 발광, 상태가 바뀔 때만 문자열/정적 UI 갱신.

런타임 스프라이트/텍스처 생성 없이 기존 Resources의 준비된 스프라이트를 재사용한다.
카메라 확대/축소나 공격 범위는 연출에 맞춰 바꾸지 않는다. 실시간 조명과 전체 화면
블룸 패스는 추가하지 않고, 국소 발광과 공유 셰이더로 선명도를 유지한다.

## 성능 예산

- 장식 스프라이트 128개 사전 준비. 초당 24회, 프레임당 3회까지 폭발 장식 허용.
- 느린 프레임에서는 파편만 6개에서 2개로 줄임. 공격과 예고 표시는 생략하지 않음.
- 각 화면의 프리즘 잔상은 최대 48개, 0.2초 길이, 최소 정점 간격 0.09.
- 프리즘 잔상 좌표는 전송하지 않음. 본체의 기존 34바이트 샘플로 재구성.
- 새 장식에는 네트워크 객체, 콜라이더, 개별 Update가 없음. 게임 난수 상태를 사용하지 않음.
- 고정된 탄환 발광의 재질/스케일/색상 변경을 캐싱. 재사용 시 레이어 목록 할당 제거.

## 재현

Unity 6000.0.68f1에서 Assets, Packages, ProjectSettings를 별도 프로젝트로 복사한다.
원본 프로젝트를 동시에 열어 검증하거나 테스트 러너를 원본 Assets에 넣지 않는다.

1. `-batchmode -executeMethod GraphicsUpgradeChecks.RunBatch`로 셰이더, 패킷,
   풀링, 벽 클리핑과 기존 전투 검증 실행. 그래픽을 켜야 벽 픽셀 검사도 수행된다.
2. `GraphicsSmokeRunner.cs`만 검증 프로젝트 Assets에 복사하고
   `-batchmode -executeMethod GraphicsSmokeRunner.Begin` 실행. `-quit/-nographics`는 생략.
   실제 Arena의 프리즘/폭발 PNG, 기본 탄환 350발 + 프리즘 64발 x 4회 부하,
   VFX 할당 및 정리 검증을 생성한다.
3. 러너를 제거한 뒤 `OnlineSetup.BuildTestBatch -graphics-validation`으로 전체 그래픽
   검사와 전투 검증을 다시 실행하고 개발 빌드 생성.
4. `RunOnlineSmoke.ps1 -PlayerPath <새 빌드> -Stress -Latency 0,50,100` 및
   일반 모드로 호스트/참가자 두 프로세스의 통신, 렌더링, 승패/재대결 검사.

현재 온라인 구조에는 클라이언트 예측/롤백이 없다. 아래 측정과 로컬 지연 시뮬레이션은
외부 Steam 회선의 지연 또는 모든 PC의 프레임을 보장하지 않는다.

## 결과

2026-10-12, Unity 6000.0.68f1 / Direct3D 11 / Intel Arc Graphics에서 실행했다.

- 기존 전투/업그레이드 검증 899개 통과. 실제 벽 밖의 폭발 픽셀 0도 검사한다.
- 그래픽 셰이더, 재질 스타일 직렬화, 34/50바이트 전송 크기, 패킷 누락/재정렬,
  프리즘 잔상 전송 제외/참가자 재현, 풀 재사용 및 초기화 검증 통과.
- 실제 경기장 Play Mode: 350발 + 프리즘 64발, 4회 반복. 첫 준비 회차 제외 518프레임.
  평균 8.70ms, p95 11.30ms, 최대 17.81ms. 목표 프레임은 120으로 설정했다.
- VFX 최대 활성 128/128, 준비 후 폭발 생성 1,000회 시도에서 관리 힙 할당 0바이트.
  포화 시 장식만 생략하며 게임 난수 상태를 바꾸지 않는 것도 검사했다.
- 랭크 서버 회귀 검증 21개 통과. 배포된 서버를 수정하지는 않았다.

실제 Windows 개발 플레이어 두 프로세스, 1280×720, 그래픽 활성화 batchmode에서
350발을 3회 생성하는 테스트도 모두 통과했다. 생성된 표시 356개는 종료 후 기본 6개로
복귀했고, 참가자는 재사용 가능한 표시 객체 356개를 넘게 생성하지 않았다.

| 지연 설정 | 호스트 평균 / 최대 | 참가자 평균 / 최대 | 최대 추정 표시 전송량 |
|---|---|---|---|
| 0ms | 2.07 / 41.37ms | 2.01 / 8.44ms | 65,504 B/s |
| 50ms | 2.02 / 23.58ms | 2.01 / 5.33ms | 65,534 B/s |
| 100ms | 2.06 / 31.38ms | 2.02 / 6.34ms | 65,534 B/s |

일반 경기 0/100ms 설정에서도 각각 2라운드의 이동, 피격, 쿨타임, 업그레이드,
동일 승패, 재대결을 호스트/참가자 모두 통과했다. 100ms 설정에서 표시된 RTT는
약 217–233ms였다. 일반 경기 검증에는 동기식 PNG 캡처가 있으므로 그 로그의
최대 프레임 지연을 순수 게임 성능 수치로 사용하지 않는다. 위 표는 캡처 없는 부하 구간이다.

테스트한 실행 폴더: `Builds/GlowGlow-Graphics-20261012`. 두 PC에 전달할 때는
실행 파일만 복사하지 말고 폴더 전체를 사용한다. 인터넷 Steam 연결/원격 PC는 검증하지 않았다.

이미지와 Play Mode 결과는 `Logs/GraphicsUpgrade/`, 전투/빌드 로그는
`Logs/graphics-build.log`에 보관한다. 멀티 결과 요약은 `Logs/GraphicsUpgrade/multiplayer-results.txt`,
원본 로그는 `Logs/ClassicOnlineSmoke/20261012-*`에 있다. 이것은 이 PC에서의 검증 결과이며,
변경 전과 동일 조건으로 측정한 성능 비교는 아니다.
